## Cadence deviation - second merge inside the 15:00 window

This pass merged records PR 330 at 15:52:45 PT, forty
minutes after the 1500 pass merged records PR 310 at
15:12:12 PT in the same 15:00-16:00 window. The body
step 2 NOTE says a pass inside a batch window where a
batch merge already happened is NOT a batch pass and
only the first pass at or after a batch point merges.
The 1530 pass applied exactly that rule fifteen minutes
before this pass and left PR 330 for the 19:00 batch.
This pass did not apply it: it relied on the checker
gate alone, whose verdict (due: yes, exit 0) is
clock-only and cannot see the earlier merge.

The deviation is cadence-only, not data: both merges
fall inside the [15:00, 16:00) window, so
`records_batch.py audit` classifies both as compliant;
PR 330 was verified clean before merging, its 12
commits are in main under merge commit e40e86a7, and
its branch was kept. No record was lost, duplicated or
misfiled. The 19:00 batch proceeds normally with PR
334.

The underlying rule tension is filed as Issue 335:
the checker gate paragraph makes the checker's verdict
the mechanical definition of due, while the first-pass
NOTE forbids a second merge in a window the checker
still calls due. Until the owner or the retro decides,
integrator passes must apply the already-merged check
on top of the checker, as the 1530 pass did.
