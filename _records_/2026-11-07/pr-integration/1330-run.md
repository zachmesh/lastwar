### False conflict call on PR 398, corrected in the same pass

During this pass I first posted a conflict note on
PR 398 (issue comment 6713288941) claiming it was
CONFLICTING at head fea2793d, based on misreading a
plain `git merge-tree <base> main <head>` output: its
"changed in both" section for
_logs_/repo-actions/action-log.jsonl looked like a
conflict. It was not. Two probes then proved it:

- A grep for `^<<<<<<<` over the plain merge-tree
  output returned zero markers for every head — but
  that probe is itself unreliable: in merge-tree
  output the markers are `+<<<<<<<`-prefixed, and
  the literal string also appears inside prose in
  merged record files, so a bare substring count
  (1 marker for fea2793d and 1cbefd1c, 3/2/1 for the
  older heads) mixes real conflicts with text
  mentions.
- The authoritative form, `git merge-tree
  --write-tree --merge-base=<base> main <head>`
  (git 2.43.0; the three-argument --write-tree form
  is a usage error, exit 129), settles it by exit
  code: exit 0 for fea2793d and for 1cbefd1c (clean
  merge), exit 1 for d5625902, 655fd4a3 and 5a15c37e
  (real conflicts). GitHub agrees: MERGEABLE/CLEAN
  for PR 398 at 1cbefd1c, CONFLICTING for the three
  older PRs.

I posted a correction on PR 398 in the same pass
(issue comment 6713373537) withdrawing the conflict
call and stating the authoritative test. Lesson for
later passes: judge mergeability by the
--write-tree --merge-base exit code (0 clean, 1
conflict), never by grepping merge-tree output for
markers and never by treating "changed in both" as
a conflict. The three older PRs' conflict findings
stand — they fail the same authoritative test.
