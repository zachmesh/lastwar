## Cadence deviation - read this first

This pass merged PR 292 at 19:31 America/Los_Angeles
(2026-11-05T03:31:46Z, merge commit
81feb1c711160890cd092b407b4ebadacb37bbac), but that
merge was NOT a sanctioned batch merge under the task
rule. The rule states that only the first pass at or
after a batch point merges, and a pass inside a batch
window where a batch merge already happened is NOT a
batch pass. A batch merge HAD already happened inside
this 1900 window: the 1900 pass merged PR 286 at 19:02
(merge commit 96aef1547a). The 1915 pass, the second
pass in the window, correctly recognised this and
merged nothing, and its run record documents the trap
in full: the checker is clock-only and still reports
due for the whole window.

This pass repeated the error the 1915 record warned
against. The checker verdict (due for the 1900 window,
28 minutes left) was taken as the batch decision
without first checking whether a batch merge had
already happened in the window, even though the 1900
pass merge of PR 286 was visible in the local main
log at pass start. The merge itself was clean and
caused no data loss: PR 292 was mergeable, merged
with a merge commit, branch kept, and its 4 commits
are now on main about three and a half hours earlier
than the 2300 batch would have landed them. No revert
was attempted: reverting a merged records batch would
churn main, remove records that are already the basis
of later branch work, and authoring a revert PR is
outside the integrator role, which reviews and merges
but does not author changes. The deviation is recorded
here, in the merge-time action-log line, and in the
PR 293 body, so the retro and the owner can judge it
from the record rather than from a clean-looking merge.
Next passes in a batch window must check the window
for an earlier batch merge before treating a checker
due verdict as a merge decision.
