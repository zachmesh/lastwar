- Merge-aware `due --merges /tmp/merges-2026-11-06.json`
  was NOT run before the merge decision. It was run
  after the merges and says: due: no - PR #374 already
  merged 2026-11-06T23:02:17-08:00 in this batch window,
  exit code 1. The merges file on the VPS already
  listed PR 374 at 2026-11-07T07:02:17Z before this
  pass started.

What the rule says (body step 2 and the 2300/2315 pass
precedent, documented in the 2330 run record): a pass
inside a batch window where a batch merge already
happened is NOT a batch pass - only the first pass at
or after a batch point merges. The 2300 pass was the
first pass at or after 23:00 and merged PR 374 at
23:02 PT. The 2330 run record stated plainly that PR
379 awaits the 03:00 batch. This pass did not read
the 2330 run record before merging, and followed the
plain checker verdict instead of the merge-aware one.

Consequence: records PR 379 merged at 23:49 PT, about
three hours before its scheduled 03:00 batch. No data
was lost or corrupted - the merge is a proper merge
commit (8cca7a39), the records/2026-11-06 branch
survives, and the merged content was verified (see
below). Nothing can or should be un-merged: main is
never rewritten. The 03:00 batch will simply have
less to merge (only post-23:49 appends).

Remediation for future passes, recorded here so the
retro can enforce it: run the merge-aware check FIRST
(`due --merges /tmp/merges-2026-11-06.json`, the file
the 2315 pass created and later passes refresh) and
read the immediately preceding pass's run record
before ANY records merge decision. The plain verdict
alone is not sufficient inside a batch window.
