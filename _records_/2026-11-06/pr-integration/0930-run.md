Verification note: the first merge-tree reading this
pass grepped for "^CONFLICT" and reported all six PRs
clean with exit code 0. That detector is wrong for
the three-argument form used here: git 2.43
`git merge-tree <base> <branch1> <branch2>` prints
conflicts as "changed in both" sections with the
conflicting content inline (and, for the clean file,
"merged" sections), and exits 0 even when conflicts
are present. The misreading was caught because the
GitHub merge states (DIRTY for the five) contradicted
it and the 0900 record reported the same five
conflicts against the same main and heads; the test
was re-run grepping "^changed in both" and confirmed
five conflicts and one clean PR before any decision
was taken. No decision rested on the first reading.
Correction to the 0900 record's note: the
"CONFLICT (content): Merge conflict in ..." lines and
the non-zero exit code belong to the --write-tree form,
not to the three-argument form used in these passes;
for this form, "^changed in both" is the detector and
the exit code is not a conflict signal.

No action-log line was added by this pass: the
batch-merge log-line rule fires at batch merges, and
this was a non-batch pass. The log line for this run
is owed at the next batch merge by that pass, as in
previous runs.
