## VPS disk-full incident and cleanup

At about 15:05 PT the merge-line step failed: `git
worktree add` on the VPS reported "fatal: cannot create
directory at '_tools_': No space left on device". Root
disk was 100% full (/dev/vda1 9.6G, 29M free); /tmp
held 2.5G in dozens of stale worktree checkouts and
~/lastwar-push held 76 consumed *.bundle transport
files. The failed step's shell chain had already
appended the merge line to the action-log in the main
worktree (wrong place, uncommitted); that stray append
was reverted immediately with `git checkout --` and no
commit or push ever carried it.

Cleanup (all content already in git, nothing
irreplaceable): removed 185 /tmp entries with mtime
older than 24h (registered worktrees via `git worktree
remove --force`, the rest via rm -rf; root-owned system
dirs such as systemd-private and certbot-log could not
be removed and were left alone) and deleted the 76
consumed *.bundle files with mtime older than 24h in
~/lastwar-push. Disk recovered to 81% (1.9G free); /tmp
2.5G to 823M. The merge-line step then succeeded on
retry. The stale scratch is a standing leak: every
pass leaves worktrees and bundles behind, and the 9.6G
root disk will fill again in days at this rate; a
periodic sweep (or a per-run cleanup of that run's own
scratch) is owed to the retro as a follow-up, not
decided here.

Related finding: the pristine action-log.jsonl on main
fails a strict per-line `json.loads` on 15 of 967 lines
(e.g. lines 3, 24, 36, 38, 40, all pre-existing, some
from 2026-11-01). The merge line added this pass was
built with `json.dumps` and validated standalone (the
new last line parses); the whole-file check is not a
gate for this log. The malformed historic lines are
left as-is; flagging them to the retro is optional.

Bundle-route lesson learned this pass: `git bundle
create` with a raw-SHA range (`8c8b68b42c..56ba1205a7`)
refuses with "Refusing to create empty bundle" even
though `git rev-list` counts 40 commits in the range,
because the bundle needs a ref as its tip. Using the
ref (`8c8b68b42c..github/main`) worked. The fetch on
the local side then needs the bundle's ref name
(`refs/remotes/github/main:main`), matching the reflog
pattern left by earlier passes.
