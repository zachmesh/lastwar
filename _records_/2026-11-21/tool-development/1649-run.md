The fix: a chain ends only when its activity ends, but the
mint must know the activity ended. The Glacieradon chain kept
minting successors after the event expired about
2026-11-14T02:05Z (timer cross-check from chain units 001 and
023) - unit 037 was enqueued at 2026-11-15T00:07:55Z, about 22
hours after the end, and the next pass spent its one live
access closing a chain that should never have been seeded.
`enqueue` now takes the latest `event_ends_at` reading
(result.stats, ISO UTC, recorded by a chain unit that reads
the event timer live) across the chain's done units in the
live pool and the given root's snapshot pool (the #750
reconciliation sources), latest by finished_at (tie-break
chain_seq) rather than the largest instant, and refuses to
mint when it is past, naming the recording unit; exit 1,
nothing minted. No reading recorded means no signal and the
mint proceeds as before; a malformed value warns and is
ignored. The mint point is `enqueue`: unit 037's frontmatter
carries the enqueue shape (empty planned_for, est 12), and
sync stages no chain successors itself, so no second guard
point is needed. Design doc gains rule R18 and changelog
0.26.0; the frontmatter version stays 0.17.0, as the 0.23.0
changelog entry records the staleness as a follow-up.

The first fixture run caught a real design error: taking the
maximum `event_ends_at` let a stale optimistic reading
override a fresh reading that said the event ended (15/17).
The guard now takes the latest reading by recency, and the
suite passes 17/17.
