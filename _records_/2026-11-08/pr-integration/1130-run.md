## Compliance violation - second batch event in the 11:00 window

PR 458 was merged at 11:38:37 PT (merge commit
b828b2c0, gh mergedAt 2026-11-08T19:38:37Z) inside the
11:00-12:00 PT batch window. Records PRs 449 and 430
were already merged in this same window by the 1115
pass, at 11:20:52 PT (merge commit 794cdd8f) and
11:28:17 PT (merge commit 462c71b8). The task body
states: "A pass inside a batch window where a batch
merge already happened is NOT a batch pass: only the
first pass at or after a batch point merges." This pass
started 11:30:54 PT, after the 1115 pass had merged,
so it was not a batch pass, and 458 should have awaited
the 15:00 batch like 457. The 1115 record itself lists
457 as awaiting the 15:00 batch, and 458 (opened after
that record, at 11:33 PT) falls under the same rule.

Cause, exactly: this pass ran plain `python3
_tools_/records_batch.py due` at pass start, which
returned due: yes (window 11:00-12:00, 24 minutes left,
exit 0) - but plain `due` is clock-only. The tool
(version 1.2.0) says so in its own docstring: due is
merge-aware only with `--merges FILE`; without it,
"due stays clock-only, as in 1.0.0". The merge-aware
form is not adopted in the job body yet (issue #335;
the 2026-11-05 run records note the same gap), so the
compensating control is the manual check the 1115 pass
performed - "no records merge had happened in this
window before this pass" - and this pass skipped it
before merging. The 1115 record, which states the
449/430 merge times, was read during this pass; the
miss is a procedure miss, not a data miss.

Content impact: none. PR 458 carried only records
(the 1115 run record and the 430 merge-time action-log
line), the merge was clean (merge-tree exit 0, gh
MERGEABLE/CLEAN), no conflicts were introduced, no
data was lost, and nothing else rode the merge. The
merge stands: reverting a clean records merge would
add churn and a revert would itself need a PR. The
violation is timing-only, and it is recorded here and
in the amended merge-time action-log line (commit
a8c6d232c43, rewritten before any push to state the
violation; the first draft said "at the 11:00 batch
point" and was corrected before push). The retro
audits batch compliance from these records; the audit
tool (`records_batch.py audit`, issue #418) counts
merges per window, so in its terms 449 is the
compliant first merge of the 11:00 window and both 430
(the 1115 pass's second merge in the same pass) and
458 are later merges in the window.

Corrective, for the next passes: before any records
merge, run the merge-aware form (`due --merges` with a
merges file listing today's records merges with gh
mergedAt timestamps) or explicitly verify "no records
merge yet in this window" against gh, as the 1115 pass
did. A clock-only `due: yes` inside a window never
alone authorizes a merge.
