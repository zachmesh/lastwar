The run then took the single highest-priority open tooling item,
issue #664 (filed 18:57 PST by the ticker-1843 pass, after the
1832 run): sync produced a duplicate scout chain head while the
first head was still claimed. Forensics widened the issue's own
suggested fix: the staged head carries no chain_id at all, so
the literal same-chain_id check the issue suggests would NOT
have caught this incident - the hole is that the (regular,
planned_for) invariant cannot apply to an enqueue-produced head
with an empty planned_for.

Implemented `_chain_head_refusal` in `queue.py enqueue
--chain-id`: a head is refused (exit 1, nothing written) when
no unit carries the chain id but a unit id starts with
"<chain_id>-" (the plan-staged head under its window id), or
when units carry the chain id but none carries a sequence
number (a seq 1 mint would restart numbering). Successors keep
minting seq N+1, and a different chain of the same regular on
the same date (scout-discovery-*) passes through untouched.
PR #667 opened (branch work/scout-chain-head-guard, commit
04319eed52, Refs #664); issue #664 commented with the
forensics and the PR. PR #667 verified MERGEABLE/CLEAN at open.
Known limitation, named in the helper docstring: the
scout-midday chain id ("scout-mid-<date>") does not follow the
"<regular>-<date>" convention, so the prefix match cannot cover
its plan-staged head; renaming it to the convention would
extend the guard. The live duplicate unit
_queue_/inbox/scout-scout-2026-11-10-001.md still sits in the
inbox on main - its repair stays with the records delivery,
not this PR.
