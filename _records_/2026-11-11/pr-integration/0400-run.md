## Process note - unnecessary git reset --hard on the VPS main worktree

- Early in this pass, before reading the 0300 run record,
  this run executed `git checkout main` followed by
  `git reset --hard FETCH_HEAD` in the shared
  ~/lastwar-push main worktree, intending to get a fresh
  main for the checker. The 0300 run record warns that
  worktree holds another job's in-flight staged changes
  and must be left untouched; the reset violated that
  standing practice. It moved local main e533edfd3 to live
  main 775e3254e.
- Checks after the fact: `git status` shows no modified or
  staged tracked files and all untracked scratch files
  (comment drafts, PR bodies) intact - reset --hard does
  not touch untracked files; no run record after 0300
  mentions staged changes still present in that worktree;
  the one dangling commit found by fsck is a 2026-11-05
  run-record commit, unrelated. No loss is identifiable,
  but the pre-reset index state cannot be reconstructed,
  so a wiped staged change cannot be strictly ruled out.
  This is recorded here for the retro, not hidden.
- Corrective rule going forward: never checkout or reset
  the shared ~/lastwar-push main worktree. The checker
  runs from a detached temp worktree of live main (as this
  pass did after the mistake, /tmp/pr-int-0400-main), and
  record commits go through a detached temp worktree of
  the records branch (as this pass did,
  /tmp/pr-int-0400-rec). A related silent failure this
  pass: `git checkout records/2026-11-11` in the main
  worktree failed because that branch is checked out in
  /tmp/td605-records; the live branch was read via
  git show / git ls-tree instead, and no write went
  through the main worktree after the reset.
- Also noted: `git merge-tree --write-tree --merge-base`
  without a value is a usage error (exit 129) on git
  2.43.0 - the plain two-commit form
  `git merge-tree --write-tree <main> <head>` is the
  correct probe, and was used for all three probes above.
